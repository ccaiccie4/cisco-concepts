Deep Dive 1 · Cisco ISE

TEAP EAP chaining: one RADIUS session, two identities

TEAP establishes a TLS-protected tunnel in Phase 1 and performs inner authentication exchanges in Phase 2. ISE 2.7+ can chain machine and user identity inside one EAP/RADIUS session, giving authorization policy compound state instead of forcing correlation of two unrelated sessions. Cisco's workflow enables TEAP and EAP chaining in Allowed Protocols, places the certificate profile in an Identity Source Sequence, invokes it from the 802.1X authentication policy, then creates authorization rules for machine-only and machine-plus-user state. Windows native TEAP support begins with Windows 10 version 2004.

Troubleshoot outer identity/TLS server trust → machine inner method → user inner method → chaining result → ISE authorization. A successful TLS tunnel proves neither inner identity nor final authorization. Use Operations > RADIUS > Live Logs to identify the exact failure stage.

Configuration workflow
Policy > Policy Elements > Results > Authentication > Allowed Protocols
Administration > Identity Management > Identity Source Sequences
Policy > Policy Sets
Operations > RADIUS > Live Logs

Deep Dive 2 · Catalyst 9800

Guest anchoring: foreign/anchor ownership and mobility-tunnel exit

The foreign controller owns the serving AP/wireless side; an anchored WLAN sends client traffic through a mobility tunnel instead of exiting locally. The anchor becomes the centralized Layer-3 exit. On the foreign, Cisco places the anchor IP under the policy profile and maps that profile to the WLAN through the AP's policy tag. Both controllers require compatible WLAN/security behavior.

Association and authentication on the foreign do not prove data forwarding. Verify mobility peer/tunnel, anchored client state, anchor-side DHCP/VLAN/routing and the actual packet exit. Changing an AP tag restarts CAPWAP and temporarily drops associations, so tag edits are service-affecting.

CLI
show wireless mobility summary
show wireless client mac-address <mac> detail
wireless profile policy anchor-policy
 mobility anchor <ip> priority 3

Deep Dive 3 · TrustSec

SXP: IP-to-SGT binding distribution when CMD is not the transport

SXP is not inline tagging. Inline CMD carries an SGT in the frame; SXP distributes IP-to-SGT bindings over a control connection so a remote enforcement point can classify traffic even when the transit network does not carry CMD. show cts sxp connections proves peer transport, while show cts sxp sgt-map proves the actual learned mappings.

An On connection therefore does not prove the expected binding exists. Cisco also documents delete hold-down behavior that can temporarily preserve mappings after a connection tears down. Trace classification source → speaker binding → SXP connection → listener mapping → destination SGT → SGACL.

CLI
show cts sxp connections
show cts sxp connections brief
show cts sxp sgt-map
show cts role-based sgt-map all

Deep Dive 4 · SD-Access

LISP Pub/Sub deployment boundary: first control-plane node and IOS XE 17.6.1+

Catalyst Center permits LISP Pub/Sub selection when the first control-plane node is added to a fabric site; Cisco documents IOS XE 17.6.1+ as the fabric-device prerequisite. The GUI path is Provision > Fabric Sites → select device → Control Plane Node → LISP Pub/Sub route distribution → Deploy.

Deployment success is controller intent. Device evidence must prove LISP sessions, local EID ownership, remote map-cache state and RLOC reachability before VXLAN forwarding can work. The engineering chain is identity/VN/SGT → EID publication → EID-to-RLOC resolution → VXLAN → destination edge → TrustSec enforcement.

Deep Dive 5 · Catalyst SD-WAN

Centralized data policy: controller intent becomes edge forwarding state

Centralized control policy affects controller routing state and advertisements and remains on the controller. Centralized data policy affects packet forwarding and is pushed read-only to selected IOS XE edges. It can match source/destination prefixes and ports, protocol, DSCP and VPN context, but only after being applied to the intended site list/direction.

show sdwan policy from-vsmart proves what the edge actually received. Then correlate the packet tuple/direction with route/TLOC and BFD state. A policy visible in Manager is not proof that a particular edge received or matched it.

CLI
show sdwan policy from-vsmart
show sdwan omp routes
show sdwan bfd sessions

Deep Dive 6 · Nexus 9000

EVPN ARP suppression: Type-2 state becomes local proxy behavior

ARP suppression lets a VTEP answer locally from EVPN-derived IP/MAC state, reducing BUM traffic; a cache miss can still flood. Cisco requires the VTEP to host the Distributed Anycast Gateway for that VNI and requires suppression configuration to match across the fabric for a VNID.

Trace remote endpoint learning → EVPN Type-2 → suppression cache → local proxy reply → unicast NVE forwarding. Release/platform support matters: Cisco documents added support on specific Nexus platforms in NX-OS 10.5(2)F and 10.6.x. At high VNI scale, Cisco also documents control-plane downtime and graceful-restart considerations.

CLI
show ip arp suppression-cache detail
show bgp l2vpn evpn
show nve peers
show nve vni

Deep Dive 7 · ACI

Contracts in hardware: APIC intent → zoning rule → packet proof

APIC contracts are declarative intent; leaves enforce compiled zoning rules. show zoning-rule exposes source/destination EPG, filter, direction, operational state, action and priority. scope <VRF_scope> narrows the table to the relevant VRF.

Troubleshoot endpoint classification → provider/consumer contract → subject/filter direction → leaf zoning realization. If APIC intent is correct but the rule is absent, the failure is policy realization. Once the rule exists, ELAM can prove the actual packet's ASIC path, connecting endpoint learning → COOP location → zoning → forwarding.

CLI
show zoning-rule
show zoning-rule scope <vrf-scope>
show endpoint ip <ip> detail

Deep Dive 8 · Secure Firewall

Lina versus Snort: why an early ALLOW can still become a deny

FTD processing crosses Lina and Snort. Rules using application, URL or geolocation can appear broad on Lina because Lina passes candidate traffic to Snort for decisive classification. An early Lina ALLOW is not necessarily final; Snort can match a deny and delete the session.

Cisco notes packet-tracer can fail to show the actual Snort rule hit in this case. Use live system support trace or system support firewall-engine-debug. Follow original tuple → NAT/connection preprocessing → Lina → Snort → verdict → egress and stop at the first phase that diverges from expectation.

CLI
show conn
show xlate
system support trace
system support firewall-engine-debug

Deep Dive 9 · Secure Client

Post-tunnel application failure: DART, routes, MTU and headend correlation

A green VPN tunnel proves establishment, not application forwarding. Cisco recommends collecting DART and client/headend evidence before changing configuration. For post-connect failure, trace client route/split-tunnel selection → virtual adapter → tunnel counters → headend session → NAT/access policy → inside route → return path.

DNS and MTU/fragmentation are independent branches; successful ICMP to one destination does not prove an application's name resolution, port policy or PMTU. Correlate DART and headend timestamps to the same session. Reinstalling the client first can destroy the evidence needed to distinguish endpoint, tunnel and headend faults.

GUI
Windows/Linux: Gear > Advanced Window > Diagnostics
macOS: Application Menu > Generate Diagnostic Report

Deep Dive 10 · IOS XE

RESTCONF process layers: HTTPS listener is not the YANG datastore

RESTCONF exposes YANG-modeled data over HTTPS. Enabling restconf starts DMI/YANG components and uses nginx as the HTTPS front end. show platform software yang-management process makes the implementation boundary visible.

HTTPS reachability does not prove the resource path, namespace, operation, authorization or datastore request is valid. Troubleshoot management IP/HTTPS → nginx → authentication/authorization → RESTCONF resource → YANG/DMI → datastore. Cisco's NETCONF documentation separately clarifies that nginx is required for RESTCONF but not NETCONF.

Deep Dive 11 · Catalyst Center

Assurance health semantics: KPI minimums, telemetry gaps and maintenance mode

Assurance health is derived from collected telemetry, not an independent forwarding truth source. Devices without location are not counted in network health and maintenance-mode entities are excluded. For switches, Cisco describes health as the minimum of relevant KPI subscores, so one poor KPI can dominate.

Telemetry Status red means full data loss and yellow partial data loss; timeline gaps mean no health data was retrieved. A gap therefore cannot be interpreted as healthy. Device 360 lets the engineer align health, issues and telemetry to the same time window. Verify observability before acting on a score.

GUI
Assurance > Health > Network
Device 360 > Telemetry Status
Device 360 > Intelligent Capture (supported APs)

Deep Dive 12 · IOS XE

NETCONF process architecture: SSH success versus RPC/YANG execution

NETCONF rides over SSH, but TCP/SSH establishment does not prove an RPC can execute. Cisco identifies ncsshd as the NETCONF SSH daemon and exposes DMI/YANG process status plus NETCONF statistics. nginx is not required for NETCONF, although it is required for RESTCONF.

Counters such as in-bad-hellos and out-rpc-errors locate different boundaries: bad hellos point early in session establishment, while RPC errors occur later. Troubleshoot reachability → SSH → NETCONF hello/capabilities → session → RPC/YANG model → authorization → datastore.
