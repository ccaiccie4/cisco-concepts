Lesson 1 · Nexus 9000 / NX-OS · VXLAN EVPN

Nexus EVPN Multi-Site: BGWs are a failure-containment boundary

VXLAN EVPN Multi-Site deliberately keeps site-local EVPN control and forwarding domains separate and interconnects them through Border Gateways (BGWs). A BGW belongs to the local site and the common inter-site domain, so both Layer-2 and Layer-3 traffic that leaves a site is steered through that boundary. This is more than a topology convention: it creates failure containment and a deterministic place to troubleshoot route reorigination, next-hop handling, DCI reachability, flood-domain behavior and tenant advertisement. Cisco requires the same Multi-Site site ID on all BGWs in a site and recommends dedicated loopbacks for NVE and Multi-Site functions. Current guidance also documents multi-hop BFD between spine and BGW loopbacks to accelerate convergence when all fabric-facing links fail. The evidence chain is local EVPN route → BGW import/advertisement → DCI EVPN peer → remote BGW → remote site import. A healthy local VTEP does not prove the BGW or DCI control plane is healthy.

Lesson 2 · Nexus 9000 / NX-OS · VXLAN EVPN

Nexus EVPN Multi-Site release behavior: next-hop reorigination changed

Release behavior matters in EVPN Multi-Site. Cisco documents that before NX-OS 9.3(5), BGWs rewrite next-hop information for EVPN routes and reoriginate them; beginning with 9.3(5), reorigination is always enabled and rewrite is not performed. That is exactly the kind of version-sensitive behavior that can make a packet-flow explanation wrong even when the high-level design is correct. During upgrades, record the running NX-OS train and the expected route attributes before and after the change. Compare EVPN NLRI, next hop, route distinguisher behavior, import policy and the NVE forwarding result rather than relying on an old runbook. Multi-Site troubleshooting should always bind observations to release because BGW route transformation is part of the control-plane contract.

Lesson 3 · Catalyst SD-WAN · Application-aware routing

Catalyst SD-WAN AAR: BFD metrics are sampled, bucketed and damped

Application-Aware Routing does not react to a single instantaneous latency or loss observation by default. BFD supplies loss, latency and jitter measurements; AAR groups observations into poll intervals and uses a multiplier to classify tunnel SLA state. Cisco documents a default 10-minute poll interval and multiplier of six in the classic model, meaning roughly one hour of measurements contributes to classification. The damping is intentional: it reduces route flapping at the cost of slower reaction. When operators shorten the poll interval or multiplier, they trade statistical confidence for reaction speed. A 10-second bucket with one BFD hello per second has only about ten samples. Troubleshoot unexpected path selection by proving the SLA class thresholds, BFD tunnel health, current app-route statistics, poll interval, multiplier, policy match and selected color. Do not infer AAR behavior from a one-off ping.

Lesson 4 · Catalyst SD-WAN · Application-aware routing

Catalyst SD-WAN Enhanced AAR: local loss and WAN loss can mean different things

Enhanced Application-Aware Routing adds PfR-based measurement and a different operational model. Cisco documents a 10-second default poll interval and multiplier of six for enhanced PfR SLA enforcement, plus explicit SLA dampening before a recovered tunnel is returned to eligible SLA buckets. This is materially different from blindly applying the classic AAR timing model. A subtle diagnostic feature is `bfd enhanced-app-route ignore-local-loss`: Cisco notes that measured loss can include local loss caused by QoS queues as well as WAN loss. If local congestion is driving the metric, moving traffic to another WAN color may not cure the underlying queue problem. Prove whether loss is local or transport-induced, then tune measurement only with enough samples to preserve confidence.

Lesson 5 · Secure Firewall / Snort 3 · Firewall performance

Secure Firewall elephant flows: inspection capacity can be consumed by a few very large sessions

Cisco defines elephant flows as unusually large, continuous flows; the documented default detection reference is greater than 1 GB over 10 seconds. A small number of such flows can consume disproportionate Snort resources and contribute to high CPU and drops. On supported Snort 3 deployments, elephant-flow handling can detect these sessions and apply remediation. The two major actions have very different security consequences. Bypass stops sending the selected flow to Snort inspection, reducing inspection load but also removing that flow from Snort analysis. Throttle continues inspection while dynamically rate-limiting the flow. Therefore the troubleshooting question is not merely 'is CPU high?' Correlate flow size/rate, Snort CPU/drop evidence, policy match, remediation action and post-change inspection behavior. Treat bypass as an explicit security tradeoff, not a generic performance knob.

Lesson 6 · Catalyst 9000 / IOS XE · Hardware forwarding

Catalyst 9000 software intent versus hardware forwarding

Catalyst forwarding failures become easier to isolate when the CPU/ASIC boundary is explicit. The Forwarding Engine Driver (FED) programs forwarding hardware and exposes punt/inject packet capture. A punt is traffic moving from the data plane toward the CPU; inject is traffic moving from CPU toward the data plane. This lets an engineer prove whether a control packet crossed the expected boundary instead of assuming that a protocol debug means the ASIC delivered the packet. The evidence order is interface/VLAN → protocol state → RIB/CEF/adjacency → hardware/FED state → targeted punt or inject capture → egress counters/capture. Scope captures to the expected tuple and stop them after reproducing the event. A healthy RIB with missing punt traffic points below the routing process; correct inject traffic with no egress points back toward hardware adjacency, VLAN or physical forwarding.

Lesson 7 · Catalyst 9800 · Wireless troubleshooting

Catalyst 9800 Radioactive Trace: follow one client instead of enabling global noise

Radioactive Trace is a conditional tracing model for Catalyst 9800 that follows a specific client or AP through distributed wireless processes. It is most useful after baseline client state identifies a boundary such as association, authentication, IP learning, policy or mobility. The trace should answer which state transition failed and which process made the decision. Cisco documents configuring a wireless MAC condition, starting conditional debugging, reproducing the problem, stopping the condition and collecting the resulting logs. Avoid tracing many MAC addresses at once because log volume and CPU cost rise. Correlate the trace timestamp with RADIUS, DHCP, DNS or packet capture at the first failing transition rather than reading thousands of unrelated messages.

Lesson 8 · Cisco ISE · AAA / segmentation

ISE dACL: authentication success does not prove authorization enforcement

A downloadable ACL is an authorization result, not an authentication method. ISE selects an Authorization Profile that references the dACL, returns the policy through RADIUS and relies on the network access device to download and enforce it. Therefore 'Access-Accept' and 'user authenticated' are not sufficient end-to-end evidence. Cisco documents failure when a referenced dACL does not exist in ISE: authorization fails and Access-Reject is returned; newer ISE releases also expose authorization-failure alarms. For a traffic failure after successful identity authentication, prove the policy-set result, returned attributes, NAD session, downloaded ACL and counters/hits. The first divergence tells you whether the problem is identity, policy selection, RADIUS delivery, object download or data-plane enforcement.

Lesson 9 · Cisco TrustSec · Segmentation

TrustSec inline SGT: identity can travel with the Ethernet frame

TrustSec inline tagging propagates the source SGT in Layer-2 metadata so downstream capable devices do not have to reconstruct the IP-to-SGT binding at every hop. This is distinct from SXP, which distributes mappings through a control-plane session. At an enforcement point, the source group and destination group feed SGACL policy. Troubleshooting therefore has separate boundaries: initial classification, tag imposition, tag transport, destination classification and SGACL enforcement. A correct matrix in ISE cannot fix a tag that disappeared at a non-CTS boundary. On port-channel designs, verify release-specific CTS requirements on the bundle and members. Packet evidence plus local SGT/SGACL state is stronger than assuming the source identity survived transit.

Lesson 10 · ACI / APIC · Endpoint forwarding

ACI endpoint learning: location must be correct before contract analysis

ACI forwarding depends on endpoint location and policy as separate layers. Leaf switches learn directly attached endpoints; endpoint information is distributed so remote leaves can resolve where traffic should go. If an endpoint is stale, learned on the wrong interface, or classified into the wrong EPG/VRF, contract analysis can be perfectly correct yet irrelevant to the actual forwarding decision. Use a staged workflow: prove source and destination endpoint learning, EPG/VRF classification and location; prove remote endpoint/control-plane knowledge; then inspect contract/provider-consumer filters and leaf zoning rules; finally use ELAM when software state still looks correct. This avoids the common mistake of changing a contract when the packet never reaches the intended enforcement context.

Lesson 11 · Catalyst Center · Assurance

Catalyst Center Path Trace: computed assurance must be bounded by supported topology

Path Trace computes a likely path from discovered topology and routing state and can augment the result with interface, ACL and QoS information. It is an excellent localization tool, but Cisco documents explicit unsupported or conditional cases, including NAT/firewall devices, vPC/VSS/M-LACP scenarios and LISP-fabric requirements for traffic/cache state. Treat the computed path as a hypothesis. If the visualization stops at a boundary, first determine whether the boundary is unsupported or discovery is stale. Then move to device-native evidence: route/FIB/adjacency, ACL/SGT/zoning rule, queue counters or packet capture. Assurance reduces the search space; it does not supersede the forwarding device.

Lesson 12 · IOS XE Programmability · Telemetry

IOS XE model-driven telemetry: model, subscription, publisher and transport are distinct failure domains

Model-driven telemetry streams YANG-modeled state through configured or dynamic subscriptions. A correct sensor path is only the first dependency. The stream, encoding and transport combination must be supported; the subscription must exist; the YANG management processes must be healthy; and the receiver connection must succeed. Cisco identifies `pubd` as the telemetry publisher and `gnmib` as the gNMI server. `show platform software yang-management process` therefore distinguishes an on-box publication failure from a collector or network problem. Troubleshoot model/path → subscription → encoding/transport → pubd/gnmib → TCP/TLS/session → receiver ingestion. A reachable collector does not prove the device is publishing.

Architecture / protocol mechanics and concept connections

EVPN Multi-Site: site-local EVPN → BGW → DCI EVPN → remote BGW → remote site. SD-WAN: BFD measurements → buckets/multiplier → SLA classification → policy-selected color, with local QoS loss separated from WAN loss when required. 802.1X/ISE: identity → authorization → dACL/SGT delivery → NAD enforcement. SD-Access: LISP location → VXLAN transport → TrustSec policy. ACI: endpoint learning → remote location knowledge → contract → leaf zoning rule → ASIC packet. IOS XE: protocol/RIB/CEF intent → FED/ASIC → packet. Telemetry: YANG path → subscription → publisher → transport → collector.

Failure-mode library
