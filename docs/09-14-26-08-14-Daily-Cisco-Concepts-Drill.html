Deep Dive 1 · Catalyst 9000 / IOS XE

Embedded Packet Capture: prove the packet boundary on-box

EPC lets IOS XE capture traffic at a device interface so an engineer can prove whether the expected packet crossed a specific forwarding boundary and what its headers looked like there. The durable workflow is capture-point definition → narrow filter/direction → start → reproduce one transaction → stop → inspect/export. An empty buffer is not automatically proof that traffic never arrived: the attachment point, direction, filter, or platform support can be wrong. Older Catalyst guidance documents restrictions on logical attachment points, which is why the capture definition itself is evidence that must be validated. Pair EPC with CEF and hardware/FED counters: software tables describe intended forwarding while the capture establishes packet presence at a real boundary. EPC is particularly useful for DHCP, ARP, routing protocols, RADIUS, and TCP handshake localization.

CLI
monitor capture <name> interface <interface> <direction>
monitor capture <name> start
monitor capture <name> stop
show monitor capture <name> buffer
monitor capture <name> export <location>

Deep Dive 2 · Catalyst 9800

Radioactive Trace: reconstruct one client state machine

Radioactive Trace scopes Catalyst 9800 debugging to a client/AP identity rather than mixing thousands of unrelated events. Follow association → security negotiation → AAA → policy → DHCP/IP learning → mobility → RUN. An Access-Accept proves only the AAA boundary; it does not prove policy realization, IP learning, or data forwarding. Cisco cautions against tracing large numbers of MAC addresses simultaneously because CPU and log volume can rise significantly. Current GUI workflow is Troubleshooting > Radioactive Trace: add the MAC/IP, apply, start, reproduce, stop, and generate. Use the trace to identify the last successful state, then inspect the dependency immediately after it.

CLI
debug platform condition start
show platform condition
show debugging
debug platform condition stop

Deep Dive 3 · Cisco ISE

TACACS+ command authorization: login is not privilege

ISE Device Administration separates authentication from authorization. TACACS Command Sets define permitted/denied commands and Shell Profiles return administrative attributes. The chain is NAD → TACACS authentication → identity store → Device Admin policy set → authorization rule → shell profile/command set → per-command request. A successful login therefore does not prove configuration commands are authorized. If show commands work but configuration commands fail, inspect the command-authorization request, matched rule, command-set expression, and device AAA method list. Network Device Groups matter because policy can depend on device type/location; a misclassified NAD can authenticate correctly yet select the wrong authorization rule.

GUI
Work Centers > Device Administration > Device Admin Policy Sets
Work Centers > Device Administration > Policy Elements > Results > TACACS Command Sets
Administration > Network Resources > Network Devices

Deep Dive 4 · Catalyst 9000 / TrustSec

SGACL enforcement: classification becomes policy only after matrix realization

TrustSec evaluates source-SGT to destination-SGT permissions. The chain is identity → SGT assignment/mapping → propagation → destination classification → SGACL matrix → hardware permit/deny. Cisco SGACL Cell Statistics expose packet counts for each source/destination SGT cell, allowing engineers to distinguish an ISE-policy assumption from actual enforcement. Seeing the correct SGT on an authentication session proves classification only; it does not prove destination mapping, policy download, enforcement placement, or hardware programming. Prove both SGTs, then permissions, then cell counters while replaying one flow. Expected deny counters localize the failure to policy; no counter movement suggests a different enforcement point or tag.

CLI
show cts role-based sgt-map all
show cts role-based permissions
show cts role-based counters

Deep Dive 5 · SD-Access

LISP EID/RLOC mechanics: map-cache bridges identity to VXLAN forwarding

The EID identifies the endpoint/address in the overlay; the RLOC identifies the fabric node that can reach it. An edge registers local EIDs, remote edges resolve them and install map-cache state pointing to the RLOC, and VXLAN carries user traffic toward that locator. Endpoint movement is therefore a control-plane convergence event, not merely a MAC-table change. A stale map-cache can black-hole traffic while the underlay IGP remains perfect. Verify local database state, remote map-cache, instance-ID/VRF context, RLOC underlay reachability, and finally VXLAN forwarding. The durable chain is EID → LISP resolution/subscription → RLOC → underlay → VXLAN → destination edge.

CLI
show lisp session
show lisp instance-id <id> ipv4 database
show lisp instance-id <id> ipv4 map-cache
show ip route <RLOC>

Deep Dive 6 · Catalyst SD-WAN

Application-Aware Routing: BFD SLA telemetry drives path policy

AAR selects transport using measured path quality, not only tunnel reachability. Cisco SLA classes use loss, latency, and jitter measured by the BFD channel between TLOCs; BFD control messages use DSCP 48. A tunnel can remain operational yet fail the application SLA. Troubleshoot application match → candidate TLOCs → BFD session → measured loss/latency/jitter → SLA class → selected action/path. If both paths violate SLA, policy fallback behavior becomes decisive. Prove the policy match before blaming BFD; otherwise the flow may never have entered the AAR decision you are analyzing.

CLI
show sdwan bfd sessions
show sdwan app-route stats
show sdwan policy from-vsmart
show policy access-lists counters

Deep Dive 7 · Nexus 9000 / NX-OS

VXLAN EVPN Type-5: routed prefixes without host-route modeling

EVPN Type-2 advertises MAC/MAC-IP endpoint information; Type-5 advertises IP prefixes. Type-5 therefore distributes internal subnet and external network reachability without representing every destination as a host MAC/IP route. Route targets control VRF import, route distinguishers provide uniqueness, and the EVPN next hop resolves toward a VTEP/border. A Type-5 route in the EVPN table is only control-plane evidence: forwarding also requires RT import, VRF RIB/FIB installation, VTEP reachability, L3VNI/NVE state, and hardware adjacency. If present in EVPN but absent from the VRF, inspect import/RT. If present in the VRF but packets fail, move to NVE/VTEP and hardware evidence.

CLI
show bgp l2vpn evpn
show bgp l2vpn evpn route-type 5
show nve peers
show nve vni
show ip route vrf <vrf> <prefix>

Deep Dive 8 · Nexus 9000 / NX-OS

vPC peer-gateway: local routing to the peer router MAC

vPC peer-gateway allows a peer to locally route packets addressed to the other peer's router MAC, avoiding unnecessary peer-link traversal in affected dual-attached designs. It does not replace the peer-link and is not the same as Layer3 peer-router. Cisco separately requires Layer3 peer-router in designs that intentionally use the vPC peer-link as a transit routing path. Keep the mechanisms separate: peer-gateway is router-MAC local handling; Layer3 peer-router concerns routing-protocol/Layer-3 behavior across vPC topology. Prove destination MAC, ingress member, vPC consistency, peer-link counters, FHRP state, and route/adjacency.

CLI
show vpc
show vpc consistency-parameters global
show interface port-channel <peer-link> counters

Deep Dive 9 · ACI / APIC

ELAM Assistant: ask the ASIC what happened to one packet

ELAM captures forwarding-engine evidence inside ACI switches. Cisco states that it can determine whether the packet reached the forwarding engine, packet properties, whether it was dropped, and which policy applied. Starting with APIC 6.1.2, ELAM Assistant is native in APIC. Use endpoint/COOP/tunnel/contract evidence to identify the suspected node, then initialize a narrow capture, trigger one packet, generate the report, wait for Report Ready, and inspect ingress fields, lookups, policy identifiers, forwarding decision, rewrite, and drop indicators. Report Ready means parsing completed, not that the packet was forwarded. Manual ELAM commands are ASIC-specific, so use the supported Assistant rather than inventing generic triggers.

Deep Dive 10 · Secure Firewall / FTD

Prefilter Fastpath: early L3/L4 policy can intentionally bypass deeper controls

Secure Firewall evaluates prefilter before normal access-control inspection. Fastpath exempts matching traffic from further inspection/control, including access control, identity requirements, and rate limiting, and can make flows eligible for offload on supported devices. Block terminates early; Analyze continues into the rest of access control. This ordering is crucial: if an application bypasses intrusion, identity, URL, or application policy, inspect prefilter before blaming the ACP because the connection may never reach it. Fastpathed events contain less application detail precisely because deep inspection was skipped. Rule order matters because the first matching rule determines the action.

GUI
Management Center: Policies > Access Control > Prefilter
Actions: Fastpath | Block | Analyze

Deep Dive 11 · Cisco Secure Client / ASA

IKEv2 remote access: separate negotiation, certificate, AAA, policy, and child SA

Secure Client IKEv2 remote access to ASA is a sequence: IKE reachability/proposal → ASA identity certificate/trustpoint → user AAA → tunnel-group/group-policy → address assignment → IKE_AUTH → child SA → protected data. Client Services on the outside interface is HTTPS used for software/profile delivery; Cisco's command reference notes that basic IKEv2 IPsec can still work when Client Services is disabled. This prevents a profile-download failure from being misdiagnosed as IKE failure. After the tunnel shows connected, routes, NAT, ACL, child-SA counters, and return path still must be proven.

CLI
crypto ikev2 enable outside client-services port 443
crypto ikev2 remote-access trustpoint <trustpoint>
group-policy <name> attributes
 vpn-tunnel-protocol ikev2
tunnel-group <name> general-attributes
 authentication-server-group <radius-group>
 address-pool <pool>

Deep Dive 12 · IOS XE / Catalyst 9000

Model-Driven Telemetry: Valid subscription is necessary, not sufficient

Model-Driven Telemetry streams YANG-modeled state through configured or dynamic subscriptions. `show telemetry ietf subscription all` exposes ID, type, state, and filter type; detail output exposes XPath, update policy, encoding, source context, receiver, and notes. Cisco troubleshooting examples show an Invalid subscription caused by a malformed XPath, proving that receiver reachability is irrelevant until the model path parses. Dynamic NETCONF subscriptions also have lifecycle semantics: they are deleted when the parent NETCONF session is torn down. For an empty collector, prove subscription existence → State Valid → model/XPath → update trigger → encoding/protocol → source VRF/route → collector socket → decode/storage.

CLI
show telemetry ietf subscription all
show telemetry ietf subscription <id> detail
clear telemetry subscription dynamic <id>

Technical figures: configured/dynamic subscription model and XPath/receiver verification in the Cisco telemetry guide.
