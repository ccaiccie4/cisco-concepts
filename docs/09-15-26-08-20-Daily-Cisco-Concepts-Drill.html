Deep Dive 1

Catalyst 9000 hardware forwarding: software intent to ASIC realization

A Catalyst forwarding problem must be decomposed into software intent and hardware realization. Protocol and policy state create RIB, adjacency, ACL, QoS, and segmentation objects; IOS XE resolves those into forwarding structures and programs the platform ASIC. A correct route alone does not prove the packet is using the intended hardware adjacency. Start with the exact tuple and expected ingress/egress, verify protocol/RIB, then CEF/FIB adjacency, interface counters, platform forwarding state, and finally packet evidence. Platform-specific FED syntax varies by Catalyst model and IOS XE release, so commands must be selected from the matching platform guide rather than guessed.

Configuration/protocol → RIB/session → FIB/adjacency → ASIC/FED → counters/capture. Preserve a software-versus-hardware mismatch before clearing state: the mismatch is evidence.

Deep Dive 2

ISE dACL authorization: Access-Accept is followed by policy download and enforcement

A downloadable ACL turns an ISE authorization decision into an enforcement object on the access switch. In ISE 3.4, dACLs are created under Policy > Policy Elements > Results > Downloadable ACLs, referenced by an Authorization Profile, and returned by a policy-set authorization rule. Cisco documents that a referenced dACL that does not exist causes authorization failure and Access-Reject, visible in Live Log Details and AAA Diagnostics. Therefore Access-Accept is not final proof: verify the authorization profile, dACL retrieval, switch authentication session, installed ACL, and packet counters.

802.1X → RADIUS → ISE authorization → authorization profile → dACL download → switch session policy → packet enforcement. During CoA/reauth, prove the previous policy was actually replaced.

Deep Dive 3

Catalyst 9800 FlexConnect: authentication and switching location are independent

FlexConnect separates where a client authenticates from where its data is switched. Connected mode can use central authentication with local switching; local authentication/local switching can operate in connected or standalone mode. Central switching depends on controller reachability, so centrally switched clients are disassociated when the AP loses the controller while locally switched sessions can survive according to WLAN state. Dynamic VLANs add another boundary: an AAA-returned VLAN must exist in the Flex AP database for the intended local behavior.

Controller reachability → WLAN auth state → AAA result/returned VLAN → Flex VLAN database → local or central data path → branch gateway. Wireless authentication does not prove the local VLAN or gateway works.

Deep Dive 4

SD-Access anycast gateway: stable first hop while endpoint location changes

Fabric edges sharing an EID subnet use a common gateway IP and MAC, giving endpoints a stable first-hop identity as they move. The edge is also a LISP xTR: local endpoint detection creates EID-table state and map-register updates the control-plane host-tracking database. Mobility therefore involves two different mechanisms: the gateway identity remains stable, while LISP location must converge to the new RLOC. Remote edges then encapsulate toward that locator with VXLAN.

Access learn → anycast gateway → EID registration → remote map resolution → RLOC underlay → VXLAN. Successful gateway ARP does not prove remote map-cache freshness.

Deep Dive 5

Catalyst SD-WAN OMP route/TLOC tuples

OMP distributes overlay reachability together with transport-locator context. Cisco documents that an IOS XE Catalyst SD-WAN device can have up to four TLOCs and by default advertises each route-TLOC tuple to the controller. The controller selects and redistributes paths subject to OMP rules and centralized policy; local ECMP limits determine installed alternatives. A prefix visible in OMP is therefore incomplete evidence unless its associated TLOC is operational and the selected tuple is installed in the local forwarding path.

Route origin → route/TLOC advertisement → controller selection/policy → edge receipt → local RIB/FIB → tunnel forwarding. Higher configured TLOC preference is preferred; equal highest preferences can ECMP.

Cisco Catalyst SD-WAN OMP guide / route-TLOC mechanics

Deep Dive 6

Nexus VXLAN EVPN ARP/ND suppression

ARP suppression lets a VTEP answer requests from EVPN-learned MAC/IP information instead of flooding every request across the fabric. Cisco requires the VTEP to host the First-Hop/Distributed Anycast Gateway for the VNI and requires suppression configuration to match across the fabric. Thus suppression depends on correct SVI/anycast-gateway and EVPN Type-2 host state. IPv6 ND suppression adds platform and TCAM considerations on supported Nexus releases.

Endpoint learn → EVPN Type-2 MAC/IP → remote suppression cache → local proxy reply → VXLAN forwarding. Inconsistent suppression or stale host state creates asymmetric symptoms; prove Type-2 state before clearing caches.

Cisco NX-OS VXLAN EVPN guide / ARP and ND suppression figures

Deep Dive 7

ACI endpoint learning and COOP: location before policy

ACI forwarding depends on endpoint location knowledge rather than only traditional MAC learning. A leaf learns locally attached endpoint state and fabric mechanisms distribute endpoint-to-leaf location so remote leaves can forward toward the correct destination leaf; COOP on the spines is central to the endpoint-directory model. When an endpoint moves, separate local learn, fabric location, VXLAN tunnel reachability, and contract/zoning-rule enforcement.

Local endpoint → fabric directory/COOP → remote resolution → destination leaf tunnel → zoning rule → egress. Do not blame contracts merely because APIC shows the endpoint; prove the remote location and tunnel first, then use ELAM when ASIC proof is needed.

Deep Dive 8

Secure Firewall Lina/Snort packet path

FTD combines connection-handling functions in Lina with Snort inspection. A useful evidence chain follows ingress classification, connection/NAT/access-control processing, any required Snort inspection, and final routing/egress. Packet-tracer evaluates many configured phases but is synthetic; when runtime behavior differs, real captures, connection state, and events are required. An ACP match is not proof that Snort or a later forwarding stage permitted the flow.

Ingress → connection/NAT/prefilter/ACP → Snort if required → route/egress. Locate the last successful stage with the exact five-tuple and capture on both sides of the suspected boundary for intermittent failures.

Deep Dive 9

Secure Access Universal ZTNA: cloud authorization to local FTD enforcement

Secure Client first establishes mTLS to Secure Access; Secure Access authenticates device/user, evaluates posture and authorization, and can issue an encrypted/signed token. For applications using FTD as a local enforcement point, Secure Access redirects the client with the token. Secure Client then establishes HTTP/2 over mTLS to FTD. Cisco documents Lina SNI handling, ZProxy token/device-certificate validation, metadata exchange, private-resource resolution, and optional Snort File/IPS policy driven by token metadata.

Client intercept → Secure Access mTLS → identity/posture/policy → signed token → FTD mTLS/SNI → ZProxy/token validation → metadata → private resource → optional Snort. Cloud authorization success does not prove the local data path.

Deep Dive 10

IOS XE BFD with BGP: rapid failure detection without waiting for BGP hold time

BFD supplies rapid forwarding-path failure detection that BGP can consume. Cisco supports BGP single-hop and multihop BFD with neighbor fall-over behavior, and documents cBit/control-plane-failure awareness plus strict mode in supported releases. Faster detection is valuable only when BFD tests the intended path reliably. Policing, path asymmetry, CPU stress, or timer mismatch can make BFD flap and cause BGP churn.

Forwarding path → BFD session/discriminators → BGP BFD association → neighbor reaction → RIB/FIB withdrawal. Verify BFD counters and reachability before assuming every BFD-down event is a real link failure.

Cisco IOS XE BFD-BGP multihop/cBit/strict-mode guide

Deep Dive 11

Catalyst Center Assurance Path Trace: expected path with documented boundaries

Path Trace calculates a path from topology and routing data collected from discovered devices and can use TCP/UDP context between wired/wireless hosts or Layer-3 interfaces. With a complete five-tuple, ACL trace can show permit/deny decisions accurately; partial tuples are best-effort. Cisco documents important limitations including NAT/firewall paths, vPC/VSS and multiple fabric scenarios. LISP fabric traces require active traffic/cache state on edges.

Catalyst Center calculated path → suspect device/interface → native counters/CEF/FED/EPC/ELAM. Assurance narrows the failure domain; it does not replace runtime packet/ASIC evidence when the two disagree.

Deep Dive 12

IOS XE PKI revocation: trust, identity, time, and status are separate checks

A trusted issuer and valid signature do not prove a certificate remains acceptable. IOS XE trustpoints can check revocation with CRL or OCSP. Cisco's revocation-check accepts ordered methods; a later method is tried when an earlier method errors. Including none as fallback changes security semantics because an unavailable revocation service can then permit acceptance without a status check. Cisco also documents CRL-size operational caveats on Catalyst guidance, recommending OCSP or smaller CRLs when files exceed documented limits.

Trust chain → device time → identity/SAN required by consuming feature → CRL/OCSP status → protocol handshake. revocation-check none may restore availability but removes revocation protection and is not a neutral fix.
