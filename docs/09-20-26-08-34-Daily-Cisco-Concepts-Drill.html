Lesson 1 · IOS XE Routing

BGP PIC Core: convergence is a forwarding-programming problem, not merely a faster SPF

BGP Prefix Independent Convergence separates failure reaction from the number of BGP prefixes affected. In a recursive design, many BGP prefixes can resolve through the same transport next hop. Without precomputation, a core failure can force repeated recursive updates. PIC Core prepares alternate recursion/output-chain information so the forwarding plane can switch the shared dependency rather than independently recomputing every service prefix.

The key distinction is PIC Core versus BGP multipath or PIC Edge. Multipath deliberately installs multiple paths for load sharing; PIC prepares a backup for convergence. Cisco documents platform-specific prerequisites and restrictions, including CEF and, on RSP3, cef table output-chain build favor convergence-speed. Hardware and release support must be checked before treating a generic PIC statement as platform fact.

TAC workflow: establish the failed transport dependency → verify IGP/LDP or underlay next-hop state → verify BGP recursive resolution → inspect CEF primary/repair programming → induce a controlled failure → prove forwarding switches to the repair path without per-prefix churn. A fast BGP best-path decision is insufficient evidence if the FIB was not preprogrammed.

Design takeaway: convergence speed depends on where repair state is programmed. Interview anchor: PIC is valuable because a common recursive dependency can be repaired independently of BGP prefix scale.

Lesson 2 · Catalyst 9800

Device Analytics: client classification depends on telemetry that may never arrive

Catalyst 9800 device analytics enriches client identity using device-originated information and shares useful context with Catalyst Center. Classification is not magic inference. Cisco documents partner/device dependencies: Apple clients can provide model information in 802.11k action frames; if those frames are absent, classification falls back to legacy HTTP/DHCP methods. Intel support is release/chipset dependent and requires AP PMF capability with PMF optional or required on the WLAN.

Local profiling is enabled globally for device classification and then in the associated policy profile. Therefore an SSID can be healthy while analytics is absent because the effective policy profile, client behavior, AP generation, central-authentication mode, PMF state, or release does not meet the feature requirements.

TAC workflow: identify the exact client and WLAN → verify global device classification → verify effective policy profile → verify AP/client support and PMF requirements → capture/trace the relevant 802.11k or DHCP/HTTP evidence → confirm controller classification → confirm export/visibility in Catalyst Center. Do not interpret “unknown device” as an RF failure.

Lesson 3 · Cisco ISE

EAP-TLS certificate trust: prove both sides of TLS before debugging authorization

EAP-TLS success requires a cryptographic identity exchange before ISE policy can make useful authorization decisions. The supplicant must trust the ISE EAP server certificate chain and validate the server identity according to its profile; ISE must trust the client certificate chain and extract an identity that maps to the intended identity source/policy. Revocation, EKU, validity, chain construction, name constraints, or identity extraction can stop the transaction before authorization.

ISE certificate stores have different purposes. A certificate trusted for admin or inter-node use is not automatically evidence that an EAP client trusts the PSN. Cisco explicitly warns that self-signed PSN certificates can cause EAP-TLS roaming failures when clients are serviced by different PSNs; externally signed CA certificates or appropriately signed wildcard deployments avoid that trust discontinuity.

TAC workflow: read the ISE detailed authentication report from the first TLS failure → verify server certificate presented by the actual PSN → validate client trust and configured server names → inspect client certificate chain/EKU/validity → verify ISE trusted CA/revocation status → confirm extracted identity → only then inspect authentication/authorization policy and returned RADIUS attributes.

Lesson 4 · Cisco TrustSec

PAC and environment data: TrustSec enforcement starts with device trust and downloaded context

A TrustSec-capable device needs more than an SGT configured somewhere in ISE. Cisco documents Protected Access Credentials (PACs) used to establish trusted policy communication, followed by environment data that includes the device SGT, TrustSec server list, SG-name table, and refresh time. show cts pac exposes PAC identity/lifetime; show cts provisioning queue helps prove provisioning state.

Environment data is operational context, not the SGACL matrix itself. This distinction matters during troubleshooting: a device may authenticate to ISE and possess a valid PAC while still having stale/missing environment data or policy. Conversely, an SGT visible in ISE does not prove the switch has downloaded or programmed the expected enforcement state.

TAC workflow: prove network device identity/RADIUS reachability → inspect PAC presence and lifetime → inspect provisioning queue → verify environment data/refresh → verify SGT mappings and SGACL policy → inspect hardware enforcement/counters → test a known source-SGT/destination-SGT flow. Re-provisioning blindly can erase the evidence that identifies the failed stage.

Lesson 5 · SD-Access

LISP Pub/Sub Dynamic Default Border: upstream loss becomes an overlay control-plane event

In SD-Access, LISP maps endpoint identity (EID) to routing location (RLOC), VXLAN carries the data plane, TrustSec supplies policy, and Catalyst Center orchestrates the fabric. LISP Pub/Sub removes the need to rely on internal BGP for normal fabric route distribution and enables capabilities such as dynamic default border, backup internet, affinity-ID, and extranet.

With dynamic default border, edge nodes subscribe to default-route information. If an external border loses its upstream BGP/default route, it updates the control plane that it can no longer provide default reachability. The control plane then updates subscribed edges so they stop using that border and use the remaining active border. This is materially different from waiting for every edge to discover a black hole in the data plane.

TAC workflow: verify upstream route/BGP on each border → verify LISP Pub/Sub control-plane registration → verify default-route publication/subscription → inspect edge map/cache state → trace VXLAN next-hop selection → validate TrustSec policy separately. Cisco recommends LISP Pub/Sub for new deployments on IOS XE 17.6+; current Catalyst Center workflows have their own border release prerequisites.

Lesson 6 · Catalyst SD-WAN

OMP best path is not forwarding viability: the chosen route still needs an active TLOC

OMP path selection evaluates overlay attributes in a defined order. Cisco documents preference, TLOC preference, origin type/subtype, origin metric, source, origin ID and other tie breakers. A controller can select multiple equal paths; by default up to four equal-cost paths can be advertised in documented cases. But a WAN edge installs an OMP route in its FIB only when the route's TLOC is active.

TLOC activity is tied to BFD. This produces a common diagnostic trap: an engineer sees the expected OMP prefix and assumes forwarding must work. If BFD to the selected TLOC is down, the control-plane route can exist in OMP evidence while the forwarding state is unusable or removed. Policy can also alter preference before the route reaches the receiving edge.

TAC workflow: compare all OMP candidates/attributes at the controller → verify policy modifications → verify what is advertised to the edge → inspect received OMP route → inspect TLOC state and BFD → verify FIB installation → test data path. Always separate “best OMP route” from “active transport locator.”

Lesson 7 · Nexus / VXLAN EVPN

ARP suppression: EVPN turns remote IP/MAC learning into first-hop proxy behavior

VXLAN EVPN ARP suppression reduces BUM traffic by maintaining an IP/MAC cache at the VTEP. Local ARP snooping and BGP EVPN advertisements populate the cache. When an attached host ARPs for a known remote IP, the first-hop leaf can answer locally with the destination MAC rather than flooding the request through the overlay.

A cache miss is intentionally different: the ARP request can be reinjected and flooded, which is necessary for unknown or silent hosts. Cisco also documents that ARP suppression must be consistently configured across the fabric and, on current Nexus 9000 guidance, is supported for a VNI when the VTEP hosts the distributed anycast first-hop gateway for that VNI.

TAC workflow: inspect host ARP request → inspect local suppression cache → verify EVPN Type-2 IP/MAC information → confirm distributed anycast gateway/SVI state → determine hit versus miss → on miss, verify VXLAN BUM replication → on hit, verify local proxy reply. A failed proxy can be an EVPN control-plane learning problem even when the NVE tunnel itself is up.

Lesson 8 · ACI / APIC

ACI endpoint evidence: follow identity and location before blaming contracts

ACI forwarding begins with endpoint learning at leaf switches. The fabric associates endpoint identity with a local attachment and distributes location information so remote leafs can reach the endpoint. Policy evaluation is a separate stage. Therefore “contract looks correct” is not enough when the fabric has learned the endpoint on the wrong leaf/interface, has stale location state, or sees repeated movement.

The durable troubleshooting model is local endpoint table → distributed endpoint/location state → VRF/bridge-domain context → zoning-rule/contract state → hardware forwarding. COOP on spines is part of the distributed endpoint-location system; APIC is the policy/controller system, not the per-packet transit path. This distinction prevents a common mistake of treating APIC GUI intent as proof of leaf hardware state.

TAC workflow: prove source and destination endpoint learning on ingress/egress leafs → verify distributed location/COOP consistency → verify BD/VRF/subnet context → verify contract/zoning rule → use ELAM when necessary to prove the packet's hardware lookup and disposition. If the endpoint moves, solve the learning/mobility cause before changing policy.

Lesson 9 · Secure Firewall

Prefilter policy: Fastpath, Block, and Analyze determine whether ACP ever sees the connection

Secure Firewall prefiltering executes before normal access-control processing and uses limited outer-header/tunnel criteria. Fastpath exempts matching traffic from further inspection and control, including access control, identity, rate limiting, and deep inspection. Block terminates it at the prefilter stage. Analyze sends it onward to the remaining access-control pipeline and can apply tunnel rezoning/inner-header processing.

This ordering is operationally critical. If a trusted tunnel was fastpathed, searching ACP/IPS events for an expected verdict is the wrong boundary: those engines never evaluated the flow. Conversely, Analyze does not mean “allow”; it means continue to subsequent controls.

TAC workflow: identify outer/inner flow tuple and tunnel → determine matching prefilter rule/action → if Analyze, follow Security Intelligence/identity/SSL/ACP/IPS/file path as applicable → inspect connection events and captures → verify final forwarding. For performance exceptions, document exactly what inspection Fastpath intentionally removes.

Lesson 10 · Catalyst 9000 / IOS XE

Software intent → CEF/FED/ASIC: prove that a correct route became correct hardware forwarding

On Catalyst 9000, a routing protocol or static configuration creates software intent; RIB/CEF resolves the forwarding adjacency; platform software programs hardware tables through the forwarding-engine infrastructure. A healthy routing protocol therefore does not prove the ASIC has the same effective state. This is why TAC workflows compare control-plane state with platform/FED evidence and counters.

Hardware troubleshooting should be hypothesis-driven. First prove the expected prefix, next hop, adjacency and egress interface in software. Then inspect platform-specific FED forwarding state and resource/counter evidence. Finally capture the packet or use supported platform tracing when the mismatch remains. Never paste a command from another Catalyst family or release without validating platform support.

TAC workflow: protocol neighbor → RIB → CEF adjacency → FED/hardware entry → ingress/egress counters → packet capture/trace. The first state boundary that differs from expectation is the failure domain. Re-verify the same chain after remediation rather than stopping when the routing protocol comes back.

Lesson 11 · Catalyst Center

Application Visibility: NBAR classification, CBAR enrichment, registry, and policy are different stages

Catalyst Center Application Visibility enables CBAR on selected devices and uses NBAR/CBAR to classify thousands of standard and custom applications. The Application Registry is the management catalog; Application Visibility provides classification; Application Policy automates QoS policy. These packages must be version-compatible. Cisco documents an NBAR provisioning scale of up to 450 interfaces on Catalyst 9000 devices, and Catalyst Center does not exceed that limit.

Unclassified traffic can be reported by a CBAR-enabled device when NBAR cannot identify it. Catalyst Center can use recommended customization/CBAR cloud sources to enrich signatures, after which discovered applications can be imported into the registry. A custom application must be assigned to an application set used by policy before policy deployment programs it.

TAC workflow: verify package compatibility → device/interface eligibility → CBAR enablement → NBAR classification/unclassified flow → registry/custom application → application-set membership → policy deployment → device-side classification/QoS state → assurance telemetry. Classification visibility and policy enforcement are related but not the same state.

Lesson 12 · Cisco Secure Client / ASA

TLS and DTLS VPN channels: UDP acceleration can fail while the secure session survives on TLS

Secure Client SSL VPN establishes the TLS channel first. DTLS can then provide a datagram transport better suited to delay-sensitive traffic. Cisco's connection-flow documentation shows that the TLS data channel continues operating while the DTLS handshake is in progress and transition occurs only after DTLS completes. If DTLS is blocked, the client retries with exponential backoff and can continue over TLS.

This explains a common field symptom: the VPN is “connected” but voice/video performance degrades. Authentication, address assignment, routes and TLS can all be healthy while UDP/DTLS is blocked by an intermediate firewall/NAT path. Cisco ASA guidance also notes that DPD is required for fallback behavior when an established DTLS path later fails.

TAC workflow: prove HTTPS/TLS connection and authentication → inspect CONNECT attributes/MTU → capture DTLS Client Hello/server response → inspect UDP reachability/NAT → verify DTLS session → compare TLS fallback behavior and MTU → test application traffic. Do not restart identity troubleshooting when the failure boundary is transport after successful authentication.
